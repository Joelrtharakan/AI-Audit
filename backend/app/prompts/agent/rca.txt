============================================================
STEP 0 — MAP THE CAUSAL CHAIN SILENTLY BEFORE PRODUCING JSON
============================================================
Work through these layers using ONLY this finding's own facts:
  1. OBSERVED CONDITION: The objective, verifiable fact (not the cause).
  2. REPORTED EXPLANATION: What a person/document claims caused it (if anything).
  3. POSSIBLE MECHANISM(S): How this finding's facts plausibly produce the condition.
     If more than one mechanism fits, name each as a separate hypothesis.
  4. VERIFICATION GAP: Exactly what evidence is missing to confirm/refute each mechanism.
  5. CONTROL/PROCESS LAYER: Only if evidence reaches this deep — what control failed.
  6. SYSTEMIC LAYER: Only if evidence reaches this deep — what explains the control weakness.

A finding can have a clear layer 1, plausible layer 3, and NOT_ESTABLISHED layers 5-6.
That is a GOOD analysis. NEVER collapse this into "root cause not established" — show the chain.

============================================================
STEP A-E — MANDATORY CAUSAL FRAMEWORK
============================================================
A. CAUSAL BOUNDARY: Identify the Trigger (what happened) vs. the Path (why the control failed).
B. DISCRIMINATION: If multiple hypotheses exist, identify the Pivot Fact — the single evidence
   item that would definitively favor one hypothesis over the others.
C. EVIDENTIARY LIMITS: Do not infer systemic failures if evidence only proves process gaps.
D. NARRATIVE QUALITY: 2-4 sentences: (1) Verified condition, (2) Named mechanism(s), (3) Known
   unknowns, (4) What evidence would discriminate between competing hypotheses.
E. RECURRENCE: A previous CAPA recorded as completed is NOT evidence of effectiveness.
F. DIRECT MECHANISM EVIDENCE: If a REPORTED statement in the evidence ledger directly confirms
   HOW the deviation occurred (e.g. a person confirms the required activity was not performed, was
   skipped, or was missed), that mechanism is SUPPORTED — do not treat it as equally uncertain
   alongside a competing mechanism the evidence contradicts (e.g. "activity happened but was not
   documented" is NOT equally plausible once a direct statement says the activity did not happen).
   Keep the supported mechanism, drop/deprioritize hypotheses the evidence contradicts, and move the
   open question one layer deeper: WHY did the confirmed mechanism occur? That deeper "why" is very
   likely still NOT_ESTABLISHED — direct evidence of the mechanism is not evidence of its root cause.
   Do not skip from mechanism straight to a root cause the evidence doesn't support.

============================================================
YOUR TASKS
============================================================

1. Determine root cause status:
   - VERIFIED: Objective records in the ledger confirm the cause.
   - SUPPORTED: Strongly supported by verified facts.
   - STATED_UNVERIFIED: Cause stated/reported but no corroborating record in ledger.
   - INFERRED: Logical conclusion without direct record confirmation.
   - NOT_ESTABLISHED: No causal signal. Cannot determine cause from available evidence.
   - CONTRADICTED: Evidence refutes the suspected cause.

2. NEVER use the observed condition as the root cause statement. The cause is NOT the observation.
   If cause is unverified, generate a LEADING HYPOTHESIS naming the plausible control failure
   using only entities and processes actually in THIS finding.

3. Assign root cause category from 6M taxonomy:
   MAN, METHOD, MACHINE, MATERIAL, MEASUREMENT, ENVIRONMENT_MGMT, OTHER.

4. Identify contributing factors — conditions only, not action items.
   Mark status as POSSIBLE_UNCONFIRMED unless supported by VERIFIED evidence.

5. Evidence-bound 5-Why analysis (max 5 steps, STOPS when evidence runs out):
   - WHY 1: Must be a VERIFIED fact directly from the finding/ledger.
   - WHY 2+: Must explain WHY a preceding fact came to be — NOT restate another fact.
     ANTI-RESTATEMENT RULE: A temporal fact is NOT a causal explanation.
     BAD: WHY were employees using the old procedure? → "Because the procedure was revised two months ago."
          (This restates when it happened — it is NOT an explanation of why the old version remained in use.)
     GOOD: WHY did the obsolete version remain in use? → "The available evidence does not establish whether
          the cause was distribution, withdrawal, electronic access, or local copies." (Status: UNKNOWN, STOP.)
   - Use ONLY entities, roles, procedures, records named in THIS finding.
   - STOP the moment the ledger cannot supply a specific answer. At that stop-point,
     state SPECIFICALLY what evidence would be needed to go one layer deeper.
   - Every question/answer must stay in this finding's own subject domain.

6. Generate 2-4 candidate hypotheses DYNAMICALLY DERIVED from this finding:
   - A documentation finding → hypotheses about workload, competency, procedure design, review controls.
   - An equipment finding → hypotheses about calibration, maintenance, operator practice, condition.
   - A supplier finding → hypotheses about qualification, incoming inspection, specification, communication.
   - A training finding → hypotheses about ASSIGNMENT, COMPLETION, RECORDKEEPING, VERIFICATION.
     Do NOT reach for "communication failure" or "supervision failure" unless those words appear in the finding.
   - Drop any hypothesis you cannot connect to something actually stated in this finding.
   - 1 hypothesis is fine. 0 is fine if nothing plausible can be named.

   For EACH hypothesis, ALL three fields are mandatory:
   - "statement": The hypothesis AND why it is plausible using this finding's own entities/facts.
   - "evidence_needed": The specific record/document that would confirm OR refute this hypothesis.
   - "discrimination_evidence": What evidence would DISTINGUISH this hypothesis from the others —
     i.e. what would be uniquely true for THIS hypothesis but false for the competing ones.
     Example: "If training assignment records show the assignment was never issued, H1 is confirmed
     and H2 (completion failure) is excluded — because H2 requires an assignment to have existed."

ABSOLUTE RULES:
- Do NOT claim VERIFIED unless a VERIFIED ledger item directly confirms the cause.
- Do NOT present REPORTED items as established facts.
- Do NOT invent identifiers, procedure names, numbers, dates, roles, or QMS features not in THIS finding.
- Do NOT reuse entities, numbers, dates, or hypotheses from any other case, example, or prior conversation.
- NOT_ESTABLISHED is a correct and valid STATUS. Only select leading_hypothesis when evidence clearly
  favors one over the others; otherwise leave null. But the NARRATIVE must walk through the causal
  layers — status=NOT_ESTABLISHED with a one-sentence narrative is a FAILURE.
- If evidence conflicts, do NOT pick a side. Say it is conflicting and requires reconciliation.
- If this finding describes a recurrence: a previous CAPA recorded as completed is NOT evidence
  that it was implemented, verified, or effective — those are separate facts requiring separate evidence.

NARRATIVE QUALITY RULE (most important single output):
The "narrative" field is what the auditor reads first. It must:
  (a) State the verified/established condition using THIS finding's own subject matter and entities.
  (b) Name the possible mechanism(s) — not "a potential cause" but the actual named hypothesis.
  (c) State explicitly what remains unknown and WHY (what evidence is absent).
  (d) If more than one mechanism is plausible, state what evidence would distinguish between them.
A narrative that could be pasted into a completely different finding without changing a word is a FAILURE.
